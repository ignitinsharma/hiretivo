# Hiretivo — Branching Strategy

## Branch Structure

```
main (production — hiretivo.com)
  ↑ merge via PR (release)
staging (QA testing — staging preview on Vercel)
  ↑ merge via PR (after dev review)
develop (default branch — dev preview on Vercel)
  ↑ merge via PR (code review)
feature/*, fix/* (dev work)
```

## Branch Purposes

| Branch | Purpose | Deployed to | Default? |
|--------|---------|-------------|----------|
| `main` | Production-ready code | hiretivo.com | No |
| `staging` | QA / pre-release testing | Vercel staging preview | No |
| `develop` | Integration of all reviewed features | Vercel dev preview | **Yes** |
| `feature/*` | Individual feature work | Auto-preview per PR | — |
| `fix/*` | Bug fixes | Auto-preview per PR | — |
| `hotfix/*` | Urgent production fixes | Auto-preview per PR | — |

---

## Feature Lifecycle

### 1. Start work

```bash
git checkout develop && git pull
git checkout -b feature/job-search
```

### 2. Develop and push

```bash
# work, commit, push
git push -u origin feature/job-search
```

### 3. Open PR to develop

- Vercel auto-creates a preview URL for the PR
- Another dev reviews the code
- On approval, merge into `develop`

### 4. Integration check on develop

- Vercel deploys the `develop` branch (dev preview)
- Team verifies features work together
- Accumulate multiple features before promoting

### 5. Promote to staging (PR: develop -> staging)

- QA team tests on the staging URL
- Bugs found? Fix on `develop`, re-merge to `staging`

### 6. Release to production (PR: staging -> main)

- Final sign-off
- Merge staging into main
- Tag the release: `v1.0.0`, `v1.1.0`, etc.

---

## Hotfix Flow (urgent production bug)

```
1. Branch from main:     git checkout main && git checkout -b hotfix/critical-bug
2. Fix and push:         git push -u origin hotfix/critical-bug
3. PR to main:           merge after review
4. Backport:             merge main back into develop and staging
```

## Branch Protection Rules

| Branch | Direct push | PR required | Approvals needed | Who can merge |
|--------|------------|-------------|------------------|---------------|
| `main` | Never | Yes | 1 | Owner only |
| `staging` | Never | Yes | 1 | Owner + lead dev |
| `develop` | Never | Yes | 1 | Any reviewer |
| `feature/*` | Yes (owner's branch) | — | — | — |

## Commit Message Format

```
type(scope): short description

feat(jobs): add skills tag input to post job form
fix(auth): correct redirect after google oauth login
chore(db): add index on application status field
refactor(matching): extract score calculation to pure function
```

Types: `feat`, `fix`, `chore`, `refactor`, `style`, `test`, `docs`

## Vercel Deployment Mapping

```
main      -> hiretivo.com (production domain)
staging   -> staging preview URL (auto-generated by Vercel)
develop   -> dev preview URL (auto-generated by Vercel)
feature/* -> auto-preview URL per PR
```

---

## Rules

1. **No direct pushes** to `develop`, `staging`, or `main` — always use PRs
2. **Every PR needs at least 1 code review** before merge
3. **Delete feature branches** after merge — keeps the repo clean
4. **Never merge staging or main backwards** into feature branches — rebase from `develop` instead
5. **Hotfixes go to main first**, then backport to `develop` and `staging`
6. **Tag every production release** on `main` with semver (`v1.0.0`)
