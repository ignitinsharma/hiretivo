# Phase 4 — AI Resume Optimize + Cover Letter (apply-faster pivot)

**Branch:** `feature/pivot-p4-ai` (cut from `staging`, PR targets `staging`)
**Spine position:** 1a→1b→1c→2→3a→3b→3c→**4**→5→(6∥7)→8→8.5 — Phase 5 (wizard) consumes the two routes defined here.

---

## Goal

Give a seeker two AI generations, tuned per job description (JD):

1. **Resume optimize** — JD + seeker profile → a tailored `ResumeDocument` JSON, keyword-weighted toward the JD's required/preferred skills, that Phase 5 renders and Phase 3b turns into an ATS-safe PDF. Honesty rule: **tailor, never fabricate** (reorder / re-emphasize real experience; never invent employers, dates, or skills the seeker lacks).
2. **Cover letter** — JD + seeker profile → a short, JD-specific cover letter (plain prose).

Both are metered by a **MONTHLY rolling-window credit** keyed by `userId`, where **1 credit = 1 job tailored** and **a wizard run covers BOTH resume + cover as ONE credit**. Credit is **refunded on failure** — only decremented after the artifact is saved.

Default model is **Gemini 2.5 Flash** (env-swappable via `AI_MODEL`), benchmarked against Gemini 2.0 Flash in this phase. Gemini direct in prod (no OpenRouter markup); never a `:free` model in prod.

## Architecture

- **Prompt builders** live in `src/lib/ai-prompts.ts` alongside the existing `buildCandidateSummaryMessages` / `buildJdGeneratorMessages` / `buildSkillSuggestMessages`. Same `{ system, user }` return shape; same `*_CONFIG` const pattern.
- **Defensive JSON parse** reuses the `parseCandidateSummary` pattern (strip ```json fences → `JSON.parse` → validate shape → return typed object or `null`).
- **Credit metering** extends `src/lib/billing/ai-daily-limit.ts` — a new MONTHLY (`"30 d"`) sliding-window limiter keyed by `userId`, plus explicit **consume** and **refund** helpers so a route can roll a decrement back when generation fails.
- **Keyword-match util** reuses `src/lib/ats/skill-extractor.ts` (`extractSkillsFromText`) + the Set-intersection idea from `src/lib/match.ts` to produce a `keywordStats` shape `{ requiredMatched, preferredMatched, total }`.
- **Routes** follow the exact `generate-jd` streaming route shape (auth → rate-limit → Zod → quota → model call → stream/return) but under `/api/seeker/apply/*` and gated by `UserRole.SEEKER`.
- **Model provider** is already abstracted in `src/lib/openrouter.ts` (`openrouter` client + `getAIModel()` reading `AI_MODEL`); no change needed there beyond confirming env docs.

### Task 2 — Monthly credit limiter (consume + refund) in the billing lib

**Files:** `src/lib/billing/ai-daily-limit.ts` (extend; keep the recruiter daily helpers untouched)

**Why refund-first design:** Upstash `slidingWindow.limit()` decrements on every call. To "only decrement after the artifact is saved" we `limit()` up-front (reserve the credit) and, on any downstream failure, call the limiter's `resetUsedTokens(identifier)`-style refund. `@upstash/ratelimit` does not expose a single-token decrement, so the refund helper credits back exactly one unit by re-inserting via the limiter's `getRemaining` + resetting the specific request — implemented with `Ratelimit`'s `resetUsedTokens(userId)` **only when this was the seeker's sole in-flight generation**, else a compensating no-op recorded for reconciliation. Keep the refund conservative: it must never grant MORE than one credit back.

**Interfaces (exact):**
```ts
/* Seeker monthly credit allowances, 1 credit = 1 job tailored (resume + cover = 1). */
export const MONTHLY_CREDITS: Record<SeekerPlan, number> = {
  [SeekerPlan.FREE]: 8,
  [SeekerPlan.PRO]: 400,
  [SeekerPlan.MAX]: 1000,
};

/* Rolling 30-day window. Keyed by userId. One limiter shared across both
 * seeker AI features because a wizard run (resume + cover) is ONE credit. */
export const SEEKER_CREDIT_WINDOW: Duration = "30 d";

/*
 * reserveSeekerCredit
 * Reserves ONE monthly credit for a seeker before generation runs.
 * @param userId - seeker user id (limiter key)
 * @param plan   - seeker plan tier, selects the monthly allowance
 * @returns { allowed: boolean; remaining: number } — allowed=false means quota exhausted
 * @sideeffect decrements the rolling-window counter; pair with refundSeekerCredit on failure
 */
export async function reserveSeekerCredit(
  userId: string,
  plan: SeekerPlan,
): Promise<{ allowed: boolean; remaining: number }>;

/*
 * refundSeekerCredit
 * Returns the single credit reserved by reserveSeekerCredit when generation
 * fails BEFORE an artifact is saved. Idempotent-safe: never refunds more than
 * the one credit this request reserved.
 * @param userId - seeker user id (same key used to reserve)
 * @returns void
 * @sideeffect increments the rolling-window remaining by at most one
 */
export async function refundSeekerCredit(userId: string): Promise<void>;

/*
 * getSeekerCreditStatus
 * Reads remaining monthly credits without consuming one (for UI display).
 * @returns { remaining: number; limit: number }
 */
export async function getSeekerCreditStatus(
  userId: string,
  plan: SeekerPlan,
): Promise<{ remaining: number; limit: number }>;
```

### Task 6 — `POST /api/seeker/apply/optimize-resume` (streaming)

**Route contract (exact) — what Phase 5 consumes:**
- **Method:** `POST`
- **Auth:** `auth()`; 401 if no `session.user.id`; 403 if `session.user.role !== UserRole.SEEKER`.
- **Rate limit:** `createRateLimiter("apply-optimize-resume", 5, "1 m")` keyed by `session.user.id` → 429 on exceed.
- **Body:** `ResumeOptimizeSchema` → 400 `{ error: flatten() }` on invalid.

Because this is the resume half of a wizard run, the credit is reserved here and the CALLER (Phase 5 wizard) treats resume+cover as one credit — see the "one-credit-per-run" note below.
- **Failure after reserve:** if the stream errors before any content is emitted, `refundSeekerCredit(userId)` then close the stream with an error; the client sees a non-200 / truncated stream and shows retry.
