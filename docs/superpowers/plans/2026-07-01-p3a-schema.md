## Goal

Add the profile-data foundation the apply wizard (Phase 5) and PDF/profile phases (3b, 3c) depend on:

1. **`Certification`** — 1:N off `SeekerProfile` (licenses/certs shown on resume + ATS forms).
2. **`ApplicationDefaults`** — 1:1 off `SeekerProfile`, holding a **global** work-authorization answer plus **optional US-EEO self-ID** fields (gender, race/ethnicity, veteran, disability). Self-ID is PII and is encrypted at rest.
3. Three new enums — **`WorkAuthStatus`**, **`SelfIdGender`**, **`SelfIdAnswer`** — added to **both** `src/constants/enums.ts` (TS) and `prisma/schema.prisma` (DB enum), kept in sync.

No application code, no UI, no API in this phase — schema + enums + one migration only.

## Architecture

- **Prisma migrations** are the source of truth (`schema.prisma` + `prisma/migrations/`). Edit schema → `pnpm prisma migrate dev` → commit the generated migration folder.
- `SeekerProfile` gains two back-relations: `certifications Certification[]` and `applicationDefaults ApplicationDefaults?`.
- Dates on `Certification` follow the repo's **`"MM/YYYY"` freeform string** convention (see `WorkExperience.startDate` / `Education.graduationDate` — `String`, not `DateTime`), so parsing/display matches existing profile models.
- TS enums live in `src/constants/enums.ts` with a matching `*_VALUES` `as const` tuple (existing house style); Prisma enums are declared in `schema.prisma`. The two must carry identical member sets.
- **Self-ID encryption:** self-ID fields are stored as `String?` ciphertext (encrypted at rest). **No field-crypto helper exists in `src/lib` today** (verified: no `encrypt`/`decrypt`/cipher usage, no crypto file, no `ENCRYPTION_KEY` env). This phase makes the columns encryption-*ready* (typed as nullable strings that will hold ciphertext) and specifies the helper contract; **building the AES-256-GCM helper is a Phase 3c / cross-cutting follow-up** (flagged in Task 5). Do NOT block 3a on the helper — the columns are inert until 3c writes to them.

## Task 5 — Field-crypto contract note + follow-up flag

**Files:** this plan only (documentation task; no code)

> **DEVIATION / flag for 3c:** DATA-MODEL's `ApplicationDefaults.selfIdGender`/`veteranStatus`/`disabilityStatus` are typed as **enum columns** (`SelfIdGender?`/`SelfIdAnswer?`), not `String?` ciphertext — this is what got shipped in Task 3, verbatim. But the DATA-MODEL PII note also says these fields must be "ENCRYPTED at rest." An enum column cannot hold opaque ciphertext (Postgres validates enum membership). 3c must resolve this contradiction before writing to these columns — either (a) keep them plaintext enums and rely on transport/DB-level encryption only, or (b) change them to `String?` ciphertext in a 3c migration and validate the plaintext enum shape at the Zod layer before encrypting. `selfIdEthnicity String?` has no such conflict — it's free text, encrypt it directly.

- [x] Record the encryption contract that Phase 3c must implement and Phase 5 must call:
  - **Helper (to build in 3c):** `src/lib/crypto/field-crypto.ts` exposing `encryptField(plaintext: string): string` / `decryptField(ciphertext: string): string`, AES-256-GCM, key from a new `FIELD_ENCRYPTION_KEY` env (32-byte base64), IV + auth-tag packed into the stored string.
  - **Confirmed gap:** no such helper or env exists today (verified — no cipher usage in `src/lib`, no `ENCRYPTION_KEY`/`FIELD_ENCRYPTION_KEY`). Columns are inert (always null) until 3c ships the helper and decides the enum-vs-ciphertext question above.
  - **Rule:** never write raw values to `selfIdEthnicity` unencrypted. `workAuth` is **not** PII and stays plaintext as the `WorkAuthStatus` enum.
